# Дополнительное задание: параллельные FastCGI-запросы

## Что изменилось в твоей работе

Раньше Main принимал запрос, читал его, считал результат и отправлял ответ.
Только после этого он переходил к следующему запросу. Если поставить sleep
перед вычислением, ждать пришлось бы всем следующим клиентам.

Теперь главный поток только принимает запросы и раздаёт их работникам.
Работники — обычные Java-потоки. По умолчанию их четыре. Один может ждать,
второй — считать, третий — отправлять ответ. Они не обязаны завершаться в порядке прихода.
Это параллельная обработка разных FastCGI-соединений. Несколько запросов
внутри одного соединения (мультиплексирование) эта реализация не поддерживает.

## Как читать Main.java

### 1. Создаём работников

```java
ExecutorService workers = Executors.newFixedThreadPool(threads);
```

ExecutorService — объект, которому можно отдать задачу. Он сам найдёт свободный
поток для её выполнения. FixedThreadPool означает, что работников фиксированное
количество. Мы не создаём отдельный новый поток на каждое нажатие кнопки.
По умолчанию threads = 4, но при запуске можно выбрать другое число.

### 2. Ограничиваем число принятых задач

```java
Semaphore slots = new Semaphore(threads);
slots.acquire();
```

Представь четыре пропуска. Главный поток берёт один пропуск перед приёмом
запроса. Когда обработка закончилась, работник возвращает его через release.
Если пропусков нет, главный поток ждёт. Это не позволяет бесконечно накапливать
принятые подключения в очереди Java. Непринятые подключения пока ждут в очереди ОС;
при большой нагрузке возможен таймаут — сервер не обещает принять сколько угодно клиентов.

### 3. Принимаем запрос только в одном потоке

```java
fastcgi.FCGIaccept();
FCGIRequest request = FCGIInterface.request;
FCGIInterface.request = null;
```

Библиотека из задания не была написана для одновременных вызовов accept:
она хранит текущий запрос в общей static-переменной и подменяет System.in/out.
Поэтому accept вызывает только главный поток. После приёма мы забираем
объект request и очищаем общую ссылку.

Зачем очищать ссылку? При следующем accept библиотека обычно закрывает
предыдущий запрос. Но теперь предыдущий запрос может ещё выполняться у работника.
Мы сообщаем библиотеке, что предыдущим соединением управляем сами.
Его закрытие выполняется в finally метода process.

Сам объект FCGIRequest содержит собственные параметры, сокет, inStream,
outStream и errStream. Внутри этих потоков выданной библиотеки используется
ссылка на этот конкретный объект, поэтому после отделения их можно передать работнику.
Эта часть решения привязана к приложенному fastcgi-lib.jar; другую библиотеку
нужно проверить отдельно, прежде чем переносить такой способ.

### 4. Передаём работу свободному потоку

```java
workers.execute(() -> {
    try {
        process(request, delay, log);
    } finally {
        slots.release();
    }
});
```

Запись `() -> { ... }` — лямбда: задача, которую нужно выполнить позже.
Главный поток отдаёт её пулу и идёт принимать следующий запрос.
Внутри задачи переменная request указывает именно на её соединение.
finally возвращает пропуск даже при ошибке. Без этого несколько ошибок
могли бы забрать все пропуска навсегда и остановить приём запросов.

### 5. Показываем долгую операцию

```java
Thread.sleep(delay);
```

Эта строка находится в process, который выполняется у работника.
Спит только текущий поток. Остальные работники и главный поток продолжают работу.
Если перенести sleep в главный цикл перед execute, приём запросов снова будет тормозить.

Задержка задаётся параметром запуска DEMO_DELAY_MS. Обычно он равен нулю.
Не нужно оставлять двухсекундную задержку для обычного использования сайта.
InterruptedException возникает, если поток попросили прервать, например при
остановке Java. Мы восстанавливаем признак прерывания и закрываем соединение.

### 6. Используем потоки конкретного запроса

```java
RequestHandler.handle(request.params, request.inStream);
request.outStream.write(body);
```

Это принципиальный момент. System.in и System.out общие для всей JVM,
а библиотека переназначает их при каждом accept. Если работник использует
System.out, он может отправить ответ уже другому клиенту.
Поэтому каждый работник читает свой inStream и пишет в свой outStream.
Строки заголовков и body записываются в методе send тем же способом.
Для журнала заранее сохранён исходный System.err — переменная log.

В process используются локальные переменные. RequestHandler создаёт свою карту
полей и свои числа для каждого вызова. AreaChecker не хранит изменяемого состояния.
Общей серверной истории у нас нет — она в браузере. Поэтому для геометрии
не требуется synchronized. Если добавить общий изменяемый ArrayList, его уже
нельзя будет бездумно изменять из нескольких потоков.

### 7. Завершаем ответ

finally в process закрывает outStream и errStream. Библиотека формирует
FastCGI-запись END_REQUEST. Затем закрывается сокет именно этого запроса.
Его закрытие не влияет на сокеты других работников. После этого возвращается пропуск.
START и END в журнале показывают имя потока и полную длительность задачи.
Поле elapsedMicros в JSON по-прежнему измеряет RequestHandler: демонстрационный
sleep расположен до него и в это число не включён. Для сравнения sleep смотри
общее время теста и END в журнале.

## Как проверить на своём компьютере

Из папки lab2, при остановленном локальном сервере:

```powershell
node tools/build.mjs
node tests/parallel.mjs
```

Тест сам запускает две отдельные Java-программы: сначала с одним работником,
затем с четырьмя. В обоих случаях sleep равен 2000 мс.
Одновременно отправляются четыре настоящих FastCGI-запроса. Каждый содержит
свой X, и тест проверяет, что ответы не перепутались.
Первый прогревочный запрос выполняется до измерения времени.

В проверенном запуске получилось:

```text
1 работник:  четыре запроса заняли 8.07 секунды
4 работника: четыре запроса заняли 2.02 секунды
```

При одном работнике задержки суммируются: 2 + 2 + 2 + 2.
При четырёх работниках четыре ожидания идут одновременно, поэтому получается
около двух секунд. Возможны небольшие отклонения из-за ОС и сети.
В журнале при четырёх работниках несколько START появляются до их END.

## Как включить задержку вручную

После сборки в одном окне:

```powershell
java -DFCGI_PORT=24001 -DFCGI_THREADS=4 -DDEMO_DELAY_MS=2000 -jar build/lab2.jar
```

Параметры `-D` ставятся до `-jar`. Для последовательного варианта замени
FCGI_THREADS=4 на FCGI_THREADS=1. Порт должен совпадать с настройкой Apache.
На Helios запуск через скрипт после переноса обновлённого комплекта:

```sh
sh /home/studs/s504568/web/lab2/server.sh stop-java
FCGI_THREADS=4 DEMO_DELAY_MS=2000 sh /home/studs/s504568/web/lab2/server.sh start-java
```

Для возврата к обычному режиму останови Java и вызови start-java без переменных.
Нужно именно перезапустить Java: запуск с новыми настройками не меняет уже работающий процесс.
Эти команды рассчитаны на обновлённый server.sh из текущего комплекта.

## Как показать через публичный адрес

Одна форма блокирует повторное нажатие, пока не получила ответ. Это защита
от случайных дублей. Открой несколько вкладок или отправь запросы одновременно
из отдельного клиента. В браузерной консоли пример выглядит так:

```javascript
const started = performance.now();
const answers = await Promise.all([0, 1, 2, 3].map(async x => {
    const response = await fetch('api/check', {
        method: 'POST',
        body: new URLSearchParams({ x: String(x), y: '0.5', r: '2' })
    });
    if (!response.ok) throw new Error(`HTTP ${response.status}`);
    return response.json();
}));
console.table(answers);
console.log('Общее время, мс:', performance.now() - started);
```

Этот пример запускается на странице лабораторной. Ответы попадут в console.table,
а не в таблицу формы. Promise.all даёт одновременные запросы на стороне клиента,
ExecutorService — независимую обработку на стороне Java. Нужны обе стороны.
Общий веб-сервер и Apache тоже должны иметь несколько свободных работников;
их загрузка может увеличить время публичного теста.

Sleep демонстрирует перекрытие ожиданий. Он не доказывает, что любые тяжёлые
вычисления станут в четыре раза быстрее: это зависит от числа ядер и характера задачи.
